# Петрович Телеметрия (Android)

Мониторинг телеметрии грузовиков через AutoGRAPH API (`https://web.tk-ekat.ru/ServiceJSON/`,
документация: https://web.tk-ekat.ru/ServiceAPI/index.html).

Стек: Kotlin, Jetpack Compose (Material 3), Retrofit + kotlinx.serialization, WorkManager, DataStore.
minSdk 26, targetSdk 35.

## Быстрый старт (Linux)

```bash
git clone git@github.com:ErmakovDenis/petrovich.git
cd petrovich
scripts/setup.sh    # JDK 17, Android SDK, эмулятор — один раз, ~5 ГБ, 10–20 минут
scripts/run.sh      # собрать, запустить эмулятор, установить и открыть приложение
```

На первом экране можно войти в AutoGRAPH или выбрать **демо-режим** (синтетические данные, логин не нужен).
Для реальных данных: «Настройки» → «Подключение и данные» → логин/пароль AutoGRAPH → «Войти и загрузить схемы».
Учётные данные **не хранятся в репозитории** — получите их у владельца проекта и не коммитьте.

Подробнее — в разделе [Сборка и запуск](#сборка-и-запуск).

## Экраны
Дизайн — по макетам «Петрович» (тёплый кремовый фон, тёмно-синий акцент, шрифты Onest и Manrope,
светлая и тёмная темы). Нижняя навигация: **Главная / Петрович / Проблемы / Настройки**.

1. **Первый запуск** — вход в AutoGRAPH или демо-данные.
2. **Главная** — приветствие и кнопка «Спросить» (в чат); карточка с проблемами (каждая строка —
   в карточку события, кнопка «Разобрать с Петровичем» — в «Проблемы») или «Всё в порядке»;
   три плашки парка «На линии / Стоят / Без связи», посчитанные по той же телеметрии, что и
   поиск аномалий (скорость последней точки, свежесть данных — см. `anomaly/classifyActivity`),
   не живой статус трекера; виджеты с «+ Добавить» (на отдельный экран) и «Настроить»
   (порядок, размер, удаление существующих); вход в «Таблицы» / «Графики»; карточка
   «Доклад на ЧЧ:ММ» — ведёт в отчёт.
3. **Проблемы** — три вкладки «Новые / В работе / Закрыты»; у новых срочных — кнопка «Разберись»
   (карточка события), у остальных новых — «Спросить Петровича»; на вкладке «Новые» под списком
   также видно, что уже передано в работу — чтобы не потерялось; проверка вручную (лупа).
4. **Карточка события** — факты, «Петрович помнит» (если на этой же машине раньше уже было такое же
   отклонение — считается по истории, не придумывается), график параметра ±3 ч вокруг события,
   честный чек-лист под графиком (скорость и зажигание в момент события — только если такие
   параметры вообще пишутся на этой машине, иначе пункт просто не показывается), «что случилось»,
   «Разберись» (открывает «Разбор») / «Ложная тревога» (с причиной).
5. **Разбор** — Петрович собирает факты и предлагает действия прямо в своей реплике: позвонить
   сотруднику (настоящий звонок через номеронабиратель, `Intent.ACTION_DIAL`, после — отмечает
   «в работе»), написать письмо (черновик с реальным PDF-вложением через настоящий `ACTION_SEND` —
   отправляет сам пользователь в своём почтовом клиенте) или отметить решённым. Выбранное действие
   ложится в ленту отдельной репликой владельца — как в сценарии макета.
6. **Петрович** — чат с локальным ассистентом по правилам и реальным данным парка (`chat/PetrovichAgent`,
   честно подписан «без внешней ИИ-модели»); с переключателем «Ассистент через стенд»
   (Настройки → Подключение и данные → Стенд) отвечает модель на стенде `ml/fleet_service` через
   `chat/RemoteChatAgent` (см. [Стенд](#стенд)), а из карточки события на стенд уходит сама аномалия
   (с хранилищем на стенде — только её id). Локальный ассистент отвечает на вопросы про конкретную машину, аномалии за неделю, кто
   больше всех жжёт топливо, связь; умеет собрать черновик письма и предложить передать случай
   сотруднику — предложенные действия показаны пилюлями прямо в ответе, подсказки-чипы видны
   постоянно; голосовой ввод — системным распознавателем речи; из карточки события открывается
   с контекстом.
7. **Настройки** — время и дни доклада, голос вкл/выкл, «Тихие часы» и лимит push, контакты
   («Кому звонить и писать» — имя, роль, телефон, почта), ссылка на «Подключение и данные»
   (AutoGRAPH, демо-режим, оформление, стенд, детектор аномалий).
8. **Таблицы и графики** — подразделы Топливо / Аккумулятор / Двигатель / Движение, период 6 ч – 7 дней.
   Машина выбирается в шапке: «◀ машина ▶» для листания и лист с поиском по названию/группе
   (сверху — машины с неразобранными аномалиями, дальше по группам); рассчитано на сотни ТС.
   Из карточки события кнопка «Графики машины» открывает графики нужной машины.

**Уведомления**: `AnomalyWorker` раз в 15 минут проверяет последние 3 часа по всем машинам; новые
аномалии сохраняются и приходят push (ночью 22:00–07:00 и сверх дневного лимита — только срочные,
настраивается). Тем же тиком, в первый раз после назначенного времени в выбранный день, уходит
разовый пуш-доклад за сутки (точность — до 15 минут, без точного будильника).

## Данные
- По умолчанию включён **демо-режим** — синтетические данные 10 машин со встроенными аномалиями.
- Для реальных данных: «Настройки» → «Подключение и данные» → логин/пароль → «Войти и загрузить схемы» (схема одна — выберется сама).
- Используемые методы API: `Login`, `EnumSchemas`, `EnumDevices`, `EnumParameters`, `GetTripTables`.

### Особенности API (проверено на реальной схеме, 7 машин: 3 × FAW, 4 × Урал NEXT)
- `GetTripTables` отдаёт точку каждые ~10 с с повторами времени: сутки по одной машине со всеми
  53 параметрами — ~17 МБ JSON. Поэтому приложение запрашивает только нужные параметры, частями по 6 ч
  (gzip включён, ~8× сжатие) и сворачивает значения в интервалы 1/2/5/15 мин для периодов 6 ч/24 ч/3 дня/7 дней
  (`data/TripTablesMapper.kt`).
- Какие параметры показываются и как агрегируются — `data/AutoGraphParameters.kt`. Дубликаты
  (`FL1` = `FLTankMain` = `TankMainFuelLevel`) и неподключённые датчики (всегда 0) скрываются.
- **Напряжение аккумулятора** есть только у Урал NEXT (`BattaryVOLTAGE`, 24 В); у FAW его нет —
  там в разделе «Аккумулятор» только флаги «Питание» и «Зажигание». При выключенном зажигании
  CAN-параметры приходят нулями, а обороты «замирают» на последнем значении — это учитывается при
  агрегации и в правилах аномалий.
- Сервер иногда не принимает соединение — запросы повторяются до 3 раз.

## Стенд

Серверная часть переезжает на стенд по плану `ml/docs/assistant-server-plan.md`. Сейчас (шаг 4) на стенде
работают ассистент, телеметрия, проверка аномалий и их хранилище: `ml/fleet_service` (FastAPI) сам загружает данные
из AutoGRAPH и сворачивает их тем же алгоритмом, что `TripTablesMapper` приложения, применяет те же правила, что
`BaselineAnomalyDetector` (совпадение держат эталоны `testdata/golden/`), вызывает `ml/predictive_antifraud` и хранит
аномалии и решения владельцев (SQLite в томе compose). Ассистент отвечает моделью через OpenRouter, получая числа
из tools `list_vehicles`, `get_vehicle_summary`, `check_vehicle`, `list_anomalies` и `get_anomaly`.
Ключи OpenRouter живут только на стенде (`ml/fleet_service/.env`), в APK их нет.

```bash
cd ml && cp fleet_service/.env.example fleet_service/.env   # заполнить FS_OPENROUTER_API_KEY и FS_LLM_MODEL
docker compose up -d --build                                # fleet_service :8080, predictive_antifraud :8001
ml/fleet_service/scripts/smoke.sh                           # сквозная проверка с подставными OpenRouter и AutoGRAPH
```

Ручная проверка приложения со стендом на реальных данных — [ml/MANUAL_CHECK.md](ml/MANUAL_CHECK.md).

В приложении: Настройки → Подключение и данные → **Стенд** → адрес (например `http://10.0.2.2:8080` для эмулятора или
`http://<IP ПК>:8080` для телефона в той же сети) → «Сохранить адрес» → включить «Ассистент через стенд»,
«Данные через стенд» и/или (раздел «Аномалии») «Аномалии со стенда» и «Хранить аномалии на стенде».
- «Аномалии со стенда»: при проверке (фоновой и кнопкой) сканер не считает аномалии на устройстве, а запрашивает
  у стенда проверку по машине и периоду (`anomaly/VehicleChecker.kt`). Лента, карточка, сводка, уведомления, решения
  и дедупликация по id остаются в приложении; id у стенда те же, поэтому лента при переключении не сбрасывается.
  Выключен — проверяет устройство, как раньше. В отладочной сборке есть «Сравнивать с устройством»: считаются оба
  варианта, расхождения пишутся в logcat с тегом `AnomalyCompare`, в ленту попадает результат по переключателю.
- «Хранить аномалии на стенде» (действует вместе с «Аномалиями со стенда»): лента, карточка и сводка читают
  аномалии со стенда, решения «Подтвердить» / «Ложная тревога» уходят на стенд и общие для всех пользователей схемы
  (в карточке видно, кто и когда решил), кнопка «Проверить» и фоновая проверка запускают проверку с сохранением
  (`anomaly/StandAnomalies.kt`, `anomaly/AnomalySync.kt`). Id выдаёт стенд: одно событие — один id при любых окнах
  проверки. `AnomalyStore` остаётся копией ленты для показа без сети; уведомления и отметка «просмотрено» — на
  устройстве. Новыми для уведомления считаются события, впервые найденные стендом после прошлого обновления ленты на
  этом устройстве (в том числе проверками других пользователей схемы), не старше суток; первое обновление — только
  точка отсчёта. При обновлении ленты локальная история переносится на стенд (по машине за запрос): стенд находит те
  же события у себя и переносит решения; итог и решения без пары — в настройках под переключателем. Записи машины,
  перенос которой не удался (стенд или AutoGRAPH не ответили), остаются на устройстве и переносятся при следующем
  обновлении. Логин AutoGRAPH (без пароля) уходит на стенд в заголовке `X-User-Name` — как автор решения. Выключен —
  всё на устройстве, как раньше; записи стенда убираются из копии ленты (у проверки на устройстве другие id).
- «Ассистент через стенд»: выключен — чат работает на заглушке, как раньше.
- «Данные через стенд»: таблицы, графики, сводка, карточка аномалии и проверка аномалий берут телеметрию со стенда
  (`data/ServerTelemetryRepository`); правила по-прежнему считает приложение. Выключен — приложение ходит
  в AutoGRAPH напрямую, как раньше. Найденные аномалии при переключении не сбрасываются: машины те же.
- Переключатели действуют только при выключенном демо-режиме.
- Доступ к стенду — по токену сессии AutoGRAPH и id схемы (заголовки `Authorization: Bearer`, `X-Schema-Id`);
  логин и пароль на стенд не передаются. Истёкший токен: приложение входит заново и повторяет запрос один раз.
- HTTP без TLS разрешён только в debug-сборке (`app/src/debug`); release ходит на стенд только по HTTPS.

Подробности, настройки `FS_*` и коды ошибок — `ml/fleet_service/README.md`.

## Место под ML-модель
- `anomaly/AnomalyDetector.kt` — общий интерфейс детектора.
- `anomaly/FeatureExtractor.kt` — матрица признаков (время × параметры) из табличных данных.
- `anomaly/MlAnomalyDetector.kt` — заготовка: положить модель в `app/src/main/assets/models/anomaly.tflite`,
  раскомментировать зависимость LiteRT в `app/build.gradle.kts` и реализовать `AnomalyModel.score()`
  (пример — в комментарии).
- Пока модели нет, работает `BaselineAnomalyDetector` — правила с порогами, сверенными с реальными данными:
  - слив по данным AutoGRAPH (`TankMainFuelDnVol`) и падение уровня топлива ≥ 25 л за 15 мин;
  - пропадание питания (кратковременное — «Инфо», без уведомления; от 2 мин — предупреждение);
  - напряжение вне нормы (12/24 В определяется автоматически) дольше 5 мин;
  - ОЖ > 100 °C, давление масла < 100 кПа при > 800 об/мин;
  - давление в тормозном контуре < 550 кПа дольше 10 мин.

  Правила по двигателю срабатывают только при включённом зажигании. Уведомления приходят для
  уровней «Предупреждение» и «Критично». Состав детекторов — в `ServiceLocator.anomalyDetector`.

## Сборка и запуск

### Требования
- **Linux x86_64** для скриптов из `scripts/` (проверено на Ubuntu 24.04). На macOS/Windows —
  через Android Studio (см. ниже).
- ~5 ГБ на диске (SDK + образ эмулятора), 8+ ГБ ОЗУ.
- `curl`, `unzip`, `tar` (`sudo apt install curl unzip`).
- Для эмулятора — аппаратная виртуализация и доступ к KVM:
  ```bash
  sudo usermod -aG kvm $USER   # затем выйти из системы и войти снова
  ```

### 1. Установка инструментов — `scripts/setup.sh`
Ставит в `~/Android` (можно переопределить `ANDROID_TOOLS_DIR`):
- JDK 17 (Temurin) — если JDK 17 ещё не установлен;
- Android SDK: platform-tools, platform 35, build-tools 34.0.0, эмулятор и образ Android 15 (x86_64);
- виртуальное устройство `petrovich` (Pixel 7, 4 ГБ ОЗУ);
- `local.properties` с путём к SDK (файл локальный, в git не попадает).

Уже установленные JDK 17 и Android SDK (из Android Studio, `$JAVA_HOME`, `$ANDROID_HOME`)
используются как есть. Повторный запуск безопасен.

```bash
scripts/setup.sh                # всё, включая эмулятор
scripts/setup.sh --no-emulator  # только для сборки (например, если тестируете на телефоне)
```

### 2. Запуск
```bash
scripts/run.sh                  # собрать, запустить эмулятор (если не запущен), установить и открыть приложение
scripts/emulator.sh             # только эмулятор (в окне)
scripts/emulator.sh --gpu host  # отрисовка через видеокарту — быстрее, см. примечание
scripts/emulator.sh --headless  # без окна
scripts/emulator.sh --wipe      # сбросить данные эмулятора
```

По умолчанию эмулятор рисует программно (`-gpu swiftshader_indirect`) — медленнее, но стабильно:
с `-gpu auto/host` в GNOME на Wayland (особенно при удалённом подключении) падал GNOME Shell.
При работе за компьютером напрямую можно попробовать `--gpu host`.

**Телефон вместо эмулятора:** включите «Отладку по USB», подключите телефон и выполните
```bash
source scripts/env.sh && ./gradlew installDebug && adb shell am start -n ru.petrovich.telemetry/.MainActivity
```

### 3. Сборка и тесты вручную
```bash
source scripts/env.sh           # JAVA_HOME / ANDROID_HOME / PATH для текущего терминала
./gradlew assembleDebug         # app/build/outputs/apk/debug/app-debug.apk
./gradlew testDebugUnitTest
# проверка правил на сохранённых ответах GetTripTables (JSON-файлы, по одной машине в файле):
REAL_TRIP_TABLES=/path/to/dir ./gradlew testDebugUnitTest
```

### Android Studio (любая ОС)
Откройте папку проекта (**File → Open**). Studio сама предложит установить недостающий SDK.
- JDK: **Settings → Build Tools → Gradle → Gradle JDK** — версия 17 (подходит встроенный JBR).
- Эмулятор: **Device Manager → Create Device** — Pixel 7, Android 15 (API 35), x86_64 или arm64
  (для Apple Silicon), затем Run ▶.

### Частые проблемы
| Симптом | Что сделать |
|---|---|
| `Нет доступа к /dev/kvm` | `sudo usermod -aG kvm $USER`, перезайти в систему |
| `Эмулятор 'petrovich' не найден` | `scripts/setup.sh` |
| `SDK location not found` | `scripts/setup.sh` (создаст `local.properties`) или открыть проект в Android Studio |
| Эмулятор очень медленный | `scripts/emulator.sh --gpu host` |
| Падает рабочий стол при запуске эмулятора | не использовать `--gpu host/auto`, запускать по умолчанию или `--headless` |
| В приложении «Не удалось загрузить данные» | сервер AutoGRAPH иногда не отвечает — нажать «Обновить»; проверить логин в Настройках |
