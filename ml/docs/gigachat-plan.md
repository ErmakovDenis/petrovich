# GigaChat как основная модель ассистента, OpenRouter как переключаемый режим

Это задание для агента-разработчика, продолжение `docs/load-and-resilience.md`. Работа идёт по шагам 1–6. После каждого
шага стенд работает по полному циклу: приложение получает данные, аномалии и ответ в чате. Шаг, после которого что-то
из этого сломано, не считается выполненным. Все новые настройки — в `Settings` (`FS_*`) с описанием в `.env.example`.

Статус на 2026-11-05: план, код не начат. Ветка `gigachat/step-1` от `resilience/step-6` (`15c78de`).

## 1. Цель и схема

Ассистент работает с GigaChat как с основной моделью. Режим OpenRouter остаётся полностью рабочим. Режим выбирается
конфигурацией сервисов.

```
FS_LLM_PROVIDER=gigachat:    fleet_service → llm_proxy → gigachat_gateway → GigaChat
FS_LLM_PROVIDER=openrouter:  fleet_service → llm_proxy → OpenRouter
```

```ini
# ml/fleet_service/.env: настройки обоих режимов лежат рядом
FS_LLM_PROVIDER=gigachat
FS_GIGACHAT_CREDENTIALS=<ключ авторизации>
FS_GIGACHAT_SCOPE=GIGACHAT_API_PERS
FS_GIGACHAT_MODEL=GigaChat-2-Pro
FS_OPENROUTER_API_KEY=<ключ OpenRouter>
FS_LLM_MODEL=openai/gpt-4o-mini
```

Правила режимов:

- Переключатель один: `FS_LLM_PROVIDER` и перезапуск compose. Образы и APK не пересобираются.
- Настройки OpenRouter (`FS_OPENROUTER_API_KEY`, `FS_LLM_MODEL`, `FS_LLM_FALLBACK_MODELS`) не переименовываются.
- Значение по умолчанию в коде — `openrouter`: обновление работающего стенда не ломает чат. В `.env.example` — `gigachat`.
- Режимы не подменяют друг друга автоматически, иначе данные могли бы незаметно уйти другому провайдеру.
  `FS_LLM_RESERVE_*` работает в обоих режимах как раньше: прокси или breaker переходят на резерв сами, поэтому резерв
  с внешним адресом получает данные без участия человека. Адрес выбирает тот, кто настраивает стенд, риск описан в `DEPLOY.md`.
- Приложение, Telegram-бот и контракт `/v1/chat` не меняются. Шаг 7 `docs/assistant-server-plan.md` не затрагивается.

## 2. Почему свой шлюз, а не провайдер LiteLLM

В закреплённом образе `ghcr.io/berriai/litellm:main-v1.83.14-stable` провайдер `gigachat` есть, но по его коду:

- авторизация идёт с `ssl_verify: False`, настройкой это не меняется: ключ уходит без проверки сертификата;
- `system` не на первом месте становится `user`, а `agent/prompt.py` шлёт до трёх системных сообщений, в том числе
  JSON аномалии с пометкой «это данные, а не инструкции»;
- `functions_state_id` выбрасывается, хотя спецификация просит возвращать его в сообщении `assistant`.

`gpt2giga` — запасной вариант: это альфа-версия (0.3.1a1), и её работа через LiteLLM не проверена. Клиент прямо в стенде
потерял бы повторы и цепочку моделей из прокси. Свой шлюз оставляет LiteLLM, breaker и метрики как есть, а TLS и
преобразование сообщений держит под нашим контролем.

## 3. Факты об API GigaChat

Из спецификации и справки на 2026-11-05. На настоящем API не проверялись: это делает человек на шаге 5.

| Тема | Что известно |
|---|---|
| OAuth | `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, Basic, заголовок `RqUID` (uuid4), поле `scope`; токен живёт 30 минут |
| Срок токена | `expires_at` в примере спецификации в секундах, LiteLLM считает его миллисекундами: разбирать оба варианта |
| Адрес API | в спецификации `https://api.giga.chat`, в LiteLLM `https://gigachat.devices.sberbank.ru/api/v1`: задаётся настройкой |
| Заголовки | без `User-Agent` `api.giga.chat` отвечает 403 |
| `system` | не первым — 422 |
| `role: function` | обязателен только `content`: JSON-объект в виде строки; поля `name` в схеме нет |
| `functions_state_id` | приходит в ответе модели, передаётся обратно в сообщении `assistant` |
| `function_call` | `name` и `arguments`; в спецификации `arguments` — JSON в строке, LiteLLM шлёт объект: **сверить на настоящем API** |
| `finish_reason` | `stop`, `length`, `function_call`, `blacklist` (тематические ограничения), `error` (невалидные аргументы функции) |
| Коды ошибок | 401 устаревший токен; 402 кончились токены модели; 422 валидация, в том числе модель без функций; 429 превышены потоки |
| Потоки | физлица 1, ИП и юрлица 10 |
| `scope` | `GIGACHAT_API_PERS` физлица, `GIGACHAT_API_B2B` пакеты, `GIGACHAT_API_CORP` pay-as-you-go |
| TLS | нужен корневой сертификат Минцифры |

## 4. Шаги

### Шаг 1. Провайдер в настройках стенда, без GigaChat

**Что сделать.**

- `config.py`: `llm_provider: Literal["openrouter", "gigachat"]`, поля `FS_GIGACHAT_*`, свойства активной модели и
  запасных; `llm_configured` — по активному провайдеру.
- `agent/llm.py`: `OpenRouterClient` становится нейтральным клиентом; `provider_preferences` — только для OpenRouter;
  `PRIMARY_ID` становится `primary`; в логах и ошибках — имя активного провайдера.
- `llm_proxy.py`: построитель копии модели по провайдеру.
- `/health`: поле `llmProvider`. `/v1/status`: провайдер и модель. Текст 503 в `api/chat.py` и описания метрик — без
  слова «OpenRouter».

**Требования по итогу.**

- [ ] С настройками по умолчанию конфигурация прокси и поведение прежние, кроме id копии `primary`.
- [ ] Все проверки зелёные.

### Шаг 2. Шлюз `gigachat_gateway`

Модуль `fleet_service/gigachat/`, запуск `python -m fleet_service.gigachat`. Эндпоинты `POST /v1/chat/completions` и `/health`.

**Что сделать.**

- Токен: кэш в памяти, обновление за 60 с до срока, одна загрузка на всех, один повтор при 401.
- TLS: проверка всегда включена, файл — `FS_GIGACHAT_CA_BUNDLE`, настройки отключения нет. Неверный файл — ошибка при старте.
- Запрос: системные сообщения склеиваются в первое; `tools` → `functions`; `tool_calls` → `function_call`;
  `tool` → `function`; результат не в виде объекта оборачивается в `{"result": ...}`; `User-Agent` всегда.
- `functions_state_id` кладётся в `id` вызова и достаётся обратно: шлюз не хранит состояния, а `agent/loop.py` передаёт
  `tool_calls` как есть.
- Ответ: `function_call` → `tool_calls`; `finish_reason: error` → ошибка; `blacklist` — текст модели, WARNING и счётчик.
- Ошибки: 402, 429, 5xx передаются с `error.code`; 422 → 400, без повторов.
- Нагрузка: `FS_GIGACHAT_CONCURRENCY` (по умолчанию 1), при истечении ожидания места — 429 с `Retry-After`.
- Настройки: `FS_GIGACHAT_CREDENTIALS`, `_SCOPE`, `_BASE_URL`, `_AUTH_URL`, `_MODEL`, `_FALLBACK_MODELS`, `_CA_BUNDLE`,
  `_CONCURRENCY`, `_TIMEOUT_SECONDS`.
- `log_masking.py`: `Basic …` и `access_token`.
- Строгий подставной GigaChat в `tests/fakes.py` по правилам справки: нет `User-Agent` — 403, `system` не первым — 422,
  результат функции не объект — 422, истёкший токен — 401.

**Требования по итогу.**

- [ ] Цикл с функцией и `functions_state_id` проходит через шлюз на подставном сервере.
- [ ] Покрыты: обновление токена, `expires_at` в секундах и миллисекундах, 402, 429, `blacklist`, `error`, предел потоков.
- [ ] Секретов нет в логах.

### Шаг 3. Compose и переключение

**Что сделать.**

- Сервис `gigachat_gateway` на образе стенда, порт не публикуется. Запускается всегда: так переключатель один, а не два
  (`FS_LLM_PROVIDER` и профиль compose). Без ключа `/health` отвечает, а чат — 503.
- Отдельный том `gigachat_config`: `gigachat.env` (права 600) видит только шлюз. Том `llm_config` прокси не подходит: образ сторонний.
- Ключ передаётся шлюзу, даже если активен OpenRouter: так проверка качества идёт до переключения.
- `llm_proxy.py`: в режиме `gigachat` группы `assistant` и `assistant-fallback-N` — `openai/<модель>` с `api_base` шлюза,
  ключ `no-key`, без `extra_body`.
- Без прокси (`FS_LLM_PROXY_URL=`) в режиме `gigachat` стенд обращается к шлюзу напрямую.
- Предел чата: в режиме `gigachat` действует меньшее из `FS_CHAT_CONCURRENCY` и `FS_GIGACHAT_CONCURRENCY`, значение видно в
  `/v1/status`. Иначе при одном потоке (`PERS`) чаты упираются в ожидание шлюза, получают 429 и открывают breaker.
  Отдельная настройка на режим не нужна: переключатель остаётся один.
- Сертификат Минцифры подключается монтированием файла. Шлюз без него не стартует, только если задан ключ.
- Проверить, что `docker compose up -d --wait` действительно пересоздаёт `llm_proxy`: `smoke.sh` использует
  `--force-recreate`, а `DEPLOY.md` обещает обычный `up -d`. Если нет — исправить через `depends_on.restart` или командой в инструкции.
- `smoke.sh`: шаг переключения туда и обратно. В режиме `gigachat` — чат с tool и ноль запросов к подставному OpenRouter;
  обратно — наоборот.

**Требования по итогу.**

- [ ] Переключение работает одной настройкой и одной командой в обе стороны.
- [ ] Ключ GigaChat не виден контейнеру `llm_proxy` и его логам.
- [ ] При одном потоке одновременные чаты идут по очереди: шлюз не отвечает 429, breaker не открывается.
- [ ] `/fleet-check` зелёный.

## 5. Риски

- **Модель может отвечать без вызова tools.** `tool_choice: required` в этом режиме недоступен, а числа должны приходить
  только из tools. Для этого нужен прогон на шаге 5.
- **Одна функция за ответ.** На каждый tool уходит отдельное обращение; сложные вопросы могут упереться в лимит итераций
  и в 100 секунд на ответ.
- **Тематические отказы.** `blacklist` может сработать на обычных вопросах про сливы топлива.
- **Переключение может не примениться к прокси.** Проверяется на шаге 3.
- **Один поток на `PERS`.** Ответы чата идут по одному: ответ с цепочкой tools держит место, а ожидание остальных входит
  в 100 секунд на ответ, так что при нескольких пользователях возможны 504 и 503. Условия тарифа для рабочих данных не проверялись.
- **Оценка на шаге 5 ручная.** Выборка небольшая, а p95 и доля отказов не измеряются (см. `docs/assistant-eval.md`).
