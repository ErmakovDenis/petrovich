# Оценка ассистента: весь конвейер

Статус на 2026-11-05: отдельная задача, не начата, не блокирует `docs/gigachat-plan.md`. Пока оценка в том плане идёт
вручную (шаг 5). Задача выделена из плана GigaChat решением владельца.

---

## 1. Зачем

`agent/eval_tools.py` отвечает на один вопрос: какой tool модель вызовет первым и с какими аргументами. Этого хватает,
чтобы отсеять запасную модель, но не хватает, чтобы сказать, хорошо ли ассистент отвечает пользователю. Цепочка tools,
итоговый текст, отказы и время ответа не оцениваются. Правка промпта, описаний tools, шлюза или лимитов сейчас ничем не
проверяется, кроме ручного сценария.

Нужна оценка всего пути от вопроса до ответа, которая служит трём целям:

- выбор модели и провайдера;
- проверка на регрессии после правок промпта, tools, шлюза и настроек;
- сравнение режимов и конфигураций на одном наборе вопросов.

```
вопрос → лимиты и сборка сообщений → прокси → шлюз или OpenRouter → модель ⇄ tools → ответ или черновик письма
```

---

## 2. Что оценивать

| Звено | Что измерять | Что есть сейчас |
|---|---|---|
| Выбор tool | верный tool и аргументы первого вызова | `eval_tools`, 25 вопросов |
| Цепочка | весь путь tools, число обращений к модели, упор в `FS_AGENT_MAX_ITERATIONS` | только строка лога ответа чата |
| Числа | каждое число в ответе есть в результатах tools | нет |
| Текст ответа | ответ по существу, честное «нет данных» | нет, только вручную |
| Отказы | доля `blacklist`, пустых ответов, ошибок, особенно на вопросах про сливы топлива | нет |
| Маршрут | доля ответов основной, запасной и резервной модели, повторы | метрика `fleet_llm_responses` и лог |
| Время | p50 и p95 всего ответа, доля модели и tools | длительность обращений к модели в метриках, общее время только в логе |
| Стоимость | токены и обращения к модели на ответ | стенд токены не учитывает |
| Письма | верные получатели и числа, нет ложного «отправлено» | нет, только вручную |
| Данные как инструкции | команды в названиях машин и текстах аномалий не выполняются | нет, только вручную |

## 3. Что сделать

1. Прогон полного цикла: настоящие `Agent`, `build_messages` и tools на фиксированных данных, модель задаётся адресом.
2. Формат набора: ожидаемая цепочка tools, числа, которые должны прозвучать, ожидаемый отказ. Текущие 25 вопросов
   переходят в него, плюс цепочки, вопросы про сливы топлива, письма и данные с вложенными командами.
3. Отчёт по метрикам из раздела 2 и сравнение двух прогонов: что стало лучше, что хуже.
4. Запуск на подставной модели в `/fleet-check`: проверяется сама оценка и механика цикла, не качество модели.
5. Пороги приёмки для шага «сменить модель» и для шага «правка промпта или tools».

`eval_tools` и его вызовы из `DEPLOY.md` и `ml/fleet_service/README.md` остаются рабочими, пока новый прогон их не заменит.
Прогоны на настоящих моделях расходуют токены и отправляют данные провайдеру: их запускает человек.

## 4. Требования по итогу

- [ ] Одна команда даёт отчёт по всем звеньям раздела 2 для заданного режима и модели.
- [ ] Два отчёта сравниваются, регрессия видна без чтения ответов целиком.
- [ ] Пороги приёмки записаны и применимы к шагу 5 плана GigaChat вместо ручной оценки.
- [ ] Числа и данные набора выдуманы: настоящие телеметрия и имена в репозиторий не попадают.

## 5. Открытые вопросы

1. **Границы конвейера.** В этом описании это путь ассистента. Включать ли детектор аномалий и `predictive_antifraud`?
2. **Как оценивать текст ответа?** Проверка по правилам дешевле и стабильнее, оценка моделью гибче, но сама даёт ошибку.
3. **Какие пороги приёмки?** Сейчас есть только «минус 5 п. п.» к основной модели по доле верных tool и аргументов.
4. **Как часто запускать на настоящих моделях?** Только при смене модели или и после правок промпта и tools.
