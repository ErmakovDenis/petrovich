# План разработки: ассистент и перенос аналитики на стенд

Это задание для агента-разработчика. Работа идёт по шагам 1–7. После каждого шага приложение и стенд
должны работать по полному циклу: пользователь открывает приложение, видит данные, получает аномалии
и ответ в чате. Шаг, после которого что-то из этого сломано, не считается выполненным.

Берите в работу один шаг за раз. Следующий шаг начинается только после того, как выполнены все
требования текущего (раздел «Требования по итогу» в каждом шаге).

---

## 1. Зачем это делается

**Сейчас.** Android-приложение само ходит в AutoGRAPH API, сворачивает телеметрию в интервалы, применяет
пороговые правила и хранит аномалии в файле на устройстве. Чат «Петрович» работает на заглушке
(`StubChatAgent`). Сервис `ml/predictive_antifraud` существует как каркас без моделей и отвечает
`ready: false`, приложение к нему не обращается. Подробности: `README.md`, `ml/ANALYTICS.md`.

**Нужно.**

1. Ассистент на LLM через OpenRouter с tool calling. Он отвечает на вопросы о состоянии автопарка по данным
   телеметрии и аналитики и может отправлять письма заранее заданным получателям.
2. Весь путь данных (загрузка из AutoGRAPH, агрегация, правила, ML, хранилище аномалий, фоновая проверка)
   переезжает из приложения на стенд.

**Почему на стенде.** Ключи OpenRouter и SMTP нельзя класть в APK. Цифры в чате и на графиках должны
считаться одним кодом, иначе они разойдутся. Отчёты по расписанию и сбор разметки для ML невозможны, пока
данные и решения по аномалиям живут только на телефоне.

**Принцип для ассистента.** Все числа считает код (tools), модель только объясняет и пересказывает их.
Если tool не дал данных, ассистент так и говорит, а не оценивает сам.

## 2. Целевая схема

```
Приложение (Kotlin)                Стенд                                   Внешние системы
┌──────────────────┐   HTTPS   ┌───────────────────────────────┐
│ экраны, кэш,     │──────────►│ fleet_service (новый, FastAPI) │──► AutoGRAPH API
│ уведомления      │           │  ├─ api: chat, vehicles,       │──► OpenRouter
│                  │◄──────────│  │       telemetry, anomalies  │──► SMTP
└──────────────────┘           │  ├─ agent: цикл LLM + tools    │
                               │  ├─ telemetry: клиент+агрегация│
                               │  ├─ rules: пороговые правила   │
                               │  ├─ store: аномалии, решения   │
                               │  └─ scheduler: фоновая проверка│
                               │ predictive_antifraud (есть)    │◄── вызывается из fleet_service
                               └───────────────────────────────┘
```

Новый сервис размещается в `ml/fleet_service/` и повторяет устройство `ml/predictive_antifraud`:
`pyproject.toml`, раскладка `src/`, настройки через `pydantic-settings`, `tests/`, `Dockerfile`,
`.env.example`, `README.md`. Префикс переменных окружения: `FS_`. Имя каталога и префикс между шагами не меняются.

## 4. Правила для всех шагов

**Старый путь остаётся рабочим до шага 7.** Каждый шаг добавляет новый путь рядом со старым и переключатель
в `AppSettings`. При выключенном переключателе приложение ведёт себя в точности как до шага. Код старого
пути удаляется только на шаге 7. Так любой шаг откатывается настройкой, без пересборки.

**Контракт данных не меняется.** Стенд отдаёт `VehicleTelemetry` и `Anomaly` в том же JSON, что уже описан в
схемах `predictive_antifraud` (camelCase, время как локальное без зоны). Модели приложения остаются прежними.
Схемы в `fleet_service` и `predictive_antifraud` должны быть одним кодом или проверяться тестом на совпадение.

**Настройки вынесены.** Ничего из перечисленного не зашивается в код: адреса, ключи, имя модели, параметры
генерации, таймауты, лимиты, системный промпт, список получателей писем, пороги правил. На стенде это
переменные `FS_*` и файлы, путь к которым задан переменной. Каждая новая настройка попадает в `.env.example`
с комментарием. В приложении остаются только адрес стенда и переключатели.

**Секреты.** Ключи и пароли не попадают в репозиторий, в APK и в логи. AutoGRAPH передаёт логин, пароль и токен
в query-строке, поэтому в логах стенда их нужно маскировать так же, как это делает `ApiFactory` в приложении.

**Время.** AutoGRAPH трактует `SD`/`ED` и возвращает время в поясе, заданном параметром `UTCOffset` при `Login`.
Везде, где стенд работает с периодами, он должен знать смещение пользователя и не подставлять свой пояс.

**Ноль не всегда значение.** При выключенном зажигании CAN-параметры приходят нулями, обороты замирают
на последнем значении, неподключённые датчики шлют 0. Правила агрегации из `TripTablesMapper` и раздела
«Особенности данных» в `ml/ANALYTICS.md` переносятся без упрощений. В ответах tools «нет данных» и «0»
различаются явно.

**Демо-режим.** До шага 7 демо-данные и их обработка остаются в приложении на старом пути. Новые
переключатели действуют только при `demoMode = false`.

**Проверки.** После каждого шага проходят: `./gradlew testDebugUnitTest`, `pytest` в `ml/predictive_antifraud`,
`pytest` в `ml/fleet_service`, сборка `./gradlew assembleDebug` и сквозной сценарий (см. шаг 1).

**Документация.** `README.md`, `ml/ANALYTICS.md` и `ml/fleet_service/README.md` обновляются в том же шаге,
в котором меняется поведение.

## 5. Шаги

### Шаг 1. Сквозной чат без данных

**Цель.** Проложить весь канал «приложение → стенд → OpenRouter → приложение» на минимальной функции, чтобы
дальше каждый шаг только добавлял tools.

**Стенд.**
- Каркас `ml/fleet_service`: приложение FastAPI, `/health`, настройки `FS_*`, Dockerfile, файл
  `docker-compose.yml` в `ml/`, поднимающий `fleet_service` и `predictive_antifraud`.
- `POST /v1/chat`: принимает историю сообщений, смещение пояса пользователя и необязательный контекст
  (объект аномалии, если чат открыт из карточки). Возвращает текст ответа.
- Клиент OpenRouter (формат совместим с OpenAI chat completions). Цикл агента уже рассчитан на tools:
  список tools пуст, но регистрация, исполнение и лимит итераций реализованы и покрыты тестом на подставном tool.
- Системный промпт лежит в файле. В нём зафиксировано: числа только из tools; данных нет, значит так и сказать.
- Доступ к `/v1/*`: приложение передаёт токен сессии AutoGRAPH пользователя и id схемы в заголовках, стенд
  проверяет токен дешёвым запросом к AutoGRAPH и кэширует результат на короткое время. Логин и пароль на стенд
  на этом шаге не передаются.

**Приложение.**
- В `AppSettings`: адрес стенда и переключатель «ассистент через стенд». Поле в экране настроек.
- `RemoteChatAgent : ChatAgent`, подключение в `ServiceLocator.chatAgent` по переключателю. Интерфейс
  `reply(history): String` на этом шаге не меняется.
- При открытии чата из карточки аномалии объект аномалии уходит в запрос как контекст.

**Сквозной сценарий.** Скрипт `ml/fleet_service/scripts/smoke.sh` (или pytest с маркером): поднять compose,
проверить `/health`, отправить вопрос в `/v1/chat`, получить непустой ответ. Внешние системы в сценарии
заменяются подставными серверами, чтобы он запускался без ключей. На следующих шагах сценарий дополняется.

**Требования по итогу.**
- [ ] При включённом переключателе вопрос из приложения возвращает ответ модели; при выключенном работает заглушка, как раньше.
- [ ] Ключ OpenRouter, модель, температура, таймаут, лимит итераций, путь к промпту и параметры маршрутизации
      провайдеров (`require_parameters`, `data_collection`) меняются через `FS_*` без правки кода.
- [ ] Запрос без токена или с недействительным токеном получает 401, в приложении это показано как понятная ошибка.
- [ ] Ошибки OpenRouter, таймаут и превышение лимита итераций возвращают осмысленное сообщение, а не 500 со стеком.
- [ ] Ключи и токены не встречаются в логах стенда и в APK.
- [ ] Ассистент без tools на вопрос о данных парка отвечает, что данных у него пока нет, и не придумывает числа
      (проверено тестом с подставной моделью и вручную на реальной).
- [ ] Сквозной сценарий проходит локально без реальных ключей.

**Вне рамок.** Телеметрия, аномалии, почта, потоковый вывод ответа.

### Шаг 2. Телеметрия через стенд

**Цель.** Стенд сам получает и агрегирует телеметрию. Приложение и ассистент читают её со стенда.

**Стенд.**
- Клиент AutoGRAPH: `EnumSchemas`, `EnumDevices`, `EnumParameters`, `GetTripTables`. Учесть: формат дат
  `yyyyMMdd-HHmm`, запросы частями по 6 ч, gzip, длина query с `onlineParams` не больше ~1900 символов,
  до 3 повторов при сетевой ошибке, защита от сбойного ответа (не больше 500 000 точек на трек).
- Перенос `TripTablesMapper` и `AutoGraphParameters` на Python: потоковый разбор, та же сетка интервалов,
  те же способы свёртки (`MEAN`, `MAX`, `MIN`, `*_NONZERO`), скрытие дубликатов и пустых столбцов.
- `GET /v1/vehicles`, `GET /v1/telemetry?vehicleId&from&to` в формате `VehicleTelemetry`.
- Кэш по ключу «схема + машина + период», а не по пользователю. Перед выдачей проверяется, что машина
  доступна этому пользователю (по его `EnumDevices`).

**Приложение.**
- `ServerTelemetryRepository : TelemetryRepository` как третий источник в `SwitchingTelemetryRepository`
  под переключателем «данные через стенд».
- Правила по-прежнему считает `BaselineAnomalyDetector` на устройстве, но уже по данным со стенда.
- Истёкший токен: стенд отвечает 401, приложение перелогинивается в AutoGRAPH и повторяет запрос один раз.

**Ассистент.** Tools `list_vehicles` и `get_vehicle_summary(vehicle_id, from, to)`. Сводка содержит
агрегаты по параметрам (минимум, максимум, среднее, последнее значение, доля интервалов с данными),
единицы измерения и период. Ряды по точкам в модель не передаются.

**Проверка совпадения.** Kotlin-тест выгружает в общий каталог (например, `testdata/golden/`) пары
«ответ `GetTripTables` → `VehicleTelemetry` в JSON» для входов из `TripTablesMapperTest`. Python-тест
строит `VehicleTelemetry` из тех же входов и сравнивает с эталоном.

**Требования по итогу.**
- [ ] При включённом переключателе экраны «Таблицы», «Графики», «Сводка» и карточка аномалии показывают данные
      со стенда; при выключенном приложение ходит в AutoGRAPH напрямую, как раньше.
- [ ] Python-агрегация совпадает с Kotlin на эталонных входах: те же столбцы, отметки времени и значения
      (допуск на вещественную арифметику задан явно).
- [ ] Есть способ запустить ту же проверку на сохранённых реальных ответах (аналог `REAL_TRIP_TABLES`).
- [ ] Пользователь не может получить телеметрию машины, которой нет в его `EnumDevices` (тест).
- [ ] Ассистент отвечает на вопрос вида «что с топливом у машины X за сутки» числами из tool; вызов tool виден в логе.
- [ ] Ответ tool ограничен по размеру и не зависит от длины периода.
- [ ] Недоступность AutoGRAPH после повторов даёт понятную ошибку в приложении и честный ответ ассистента.
- [ ] Сквозной сценарий дополнен: машины → телеметрия → вопрос с вызовом tool.

**Вне рамок.** Правила на стенде, хранилище, фоновая проверка.

### Шаг 3. Правила и аналитика на стенде

**Цель.** Аномалии считает стенд. Ассистент получает доступ к проверкам и к аналитическому сервису.

**Стенд.**
- Точный перенос `BaselineAnomalyDetector` на Python: те же типы (`drain`, `drop`, `power`, `volt`,
  `overheat`, `oil`, `brake`), пороги, логика эпизодов и формат id. Пороги вынесены в настройки, значения
  по умолчанию равны текущим.
- Вызов `predictive_antifraud` (`/v1/predictive/analyze`, `/v1/antifraud/check`) по HTTP; адрес и `X-API-Key`
  в настройках.
- `POST /v1/anomalies/check` с телом `{vehicleId, from, to}`: стенд сам берёт телеметрию, применяет правила,
  вызывает аналитику и возвращает список `Anomaly` и статус готовности моделей. Результат не сохраняется.

**Приложение.**
- `AnomalyDetector.detect()` принимает готовую телеметрию. Отправлять на стенд телеметрию, только что
  полученную со стенда, нельзя. Нужен шов на уровне `AnomalyScanner`: под переключателем «аномалии со стенда»
  сканер запрашивает `check` по машине и периоду. Локальный `AnomalyStore`, дедупликация и уведомления остаются.
- Режим сравнения для отладочной сборки: считаются оба варианта, расхождения пишутся в лог, пользователю
  показывается результат по переключателю.

**Ассистент.** Tool `check_vehicle(vehicle_id, from, to)`: аномалии по правилам и результат аналитики.
Если модели не загружены, в ответе tool есть явное поле об этом, и ассистент сообщает пользователю,
что предиктивная проверка недоступна, а не что нарушений нет.

**Проверка совпадения.** Kotlin-тест выгружает эталон «`VehicleTelemetry` → список аномалий» для демо-машин
из `AnomalyDetectionTest`. Python-тест сравнивает id, тип, важность и время события.

**Требования по итогу.**
- [ ] На эталонных входах списки аномалий Python и Kotlin совпадают по id, типу, важности и времени события.
- [ ] Есть способ запустить сравнение на сохранённых реальных данных.
- [ ] При включённом переключателе лента, карточка, сводка и уведомления работают на аномалиях со стенда;
      при выключенном считает устройство, как раньше.
- [ ] Недоступность `predictive_antifraud` не ломает проверку по правилам; статус аналитики в ответе отражён.
- [ ] Ассистент различает три исхода: аномалии найдены, не найдены, проверка недоступна (тесты с подставной моделью).
- [ ] Пороги правил меняются настройкой без правки кода.
- [ ] Сквозной сценарий дополнен: проверка машины и вопрос об аномалиях.

**Вне рамок.** Исправление нестабильных id (проблема 1 в `ml/ANALYTICS.md`) делается на шаге 4, здесь нужен точный перенос.

### Шаг 4. Хранилище аномалий и решений

**Цель.** Аномалии и решения владельцев хранятся на стенде и доступны ассистенту.

**Стенд.**
- База данных (адрес в настройках, миграции схемы в репозитории): аномалии, решения
  (`CONFIRMED` / `FALSE_ALARM`, причина, кто и когда), отметка последней успешной проверки по схеме.
- Стенд становится владельцем id. Проверка для сохранения всегда идёт на одной канонической сетке,
  привязанной к фиксированному началу отсчёта, независимо от длины окна и момента запуска.
- `GET /v1/anomalies` с фильтрами (период, машина, важность, статус разбора), `POST /v1/anomalies/{id}/resolve`,
  `POST /v1/anomalies/scan` (проверка по запросу с сохранением).
- Разовая загрузка локальных решений с устройства. Так как id меняются, сопоставление идёт по типу, машине,
  параметру и времени события с допуском.

**Приложение.**
- Под переключателем лента, карточка и сводка читают аномалии со стенда, решения отправляются на стенд.
  `AnomalyStore` остаётся локальным кэшем для показа без сети.
- Кнопка «Проверить» вызывает `scan` на стенде.
- Чат из карточки передаёт только `anomalyId`.

**Ассистент.** Tools `list_anomalies` (с теми же фильтрами, ответ ограничен по числу записей и содержит общее
количество) и `get_anomaly(id)`.

**Требования по итогу.**
- [ ] Одно и то же событие получает один id при повторных проверках с разными окнами и в разное время (тест).
- [ ] Повторная проверка не создаёт дубликатов в ленте.
- [ ] Решение, принятое в приложении, сохраняется на стенде и видно после переустановки приложения.
- [ ] Локальные решения, принятые до шага, перенесены; несопоставленные перечислены в отчёте о переносе, а не потеряны молча.
- [ ] Пользователь видит и меняет только аномалии машин из своей схемы (тест).
- [ ] Ассистент отвечает на «какие аномалии за сутки» и «что решили по этой аномалии» данными из хранилища.
- [ ] Без сети приложение показывает последнюю загруженную ленту и не падает.
- [ ] Данные хранилища переживают перезапуск контейнера.
- [ ] Сквозной сценарий дополнен: проверка с сохранением → лента → решение → вопрос ассистенту.

**Вне рамок.** Проверка по расписанию.

### Шаг 5. Фоновая проверка на стенде

**Перед началом нужен ответ владельца проекта.** Проверка без телефона требует постоянного доступа стенда
к AutoGRAPH от имени пользователя. Варианты: хранить логин и пароль на стенде в зашифрованном виде или
работать на токене сессии, пока он жив (срок жизни токена нужно измерить). Не выбирайте вариант самостоятельно:
запросите решение и реализуйте выбранный.

**Стенд.**
- Планировщик: проверка по каждой активной схеме с заданным интервалом и окном (сейчас 15 минут и 3 часа,
  оба значения в настройках). Одна схема проверяется один раз независимо от числа пользователей.
- Ограничение параллельных запросов к AutoGRAPH (сейчас в приложении не больше 2).
- Отметка последней проверки не обновляется, если ни одна машина не ответила. Это повторяет поведение
  `AnomalyScanner`, иначе сводка сообщит «всё в порядке» при недоступном источнике.
- Хранение доступа по решению владельца. Смещение пояса пользователя сохраняется вместе с доступом.

**Приложение.**
- Под переключателем `AnomalyWorker` не считает сам, а запрашивает у стенда аномалии новее последней
  полученной и показывает уведомления через `AnomalyNotifier` с учётом настроек `pushCritical` / `pushWarning`.
- Сводка берёт время последней проверки со стенда.

**Требования по итогу.**
- [ ] Аномалия появляется в ленте и приходит уведомлением, когда приложение не запускалось между событием и проверкой.
- [ ] Одна аномалия даёт одно уведомление, включая случай двух устройств одного пользователя.
- [ ] Две учётные записи одной схемы не удваивают запросы к AutoGRAPH (тест с подставным сервером).
- [ ] При недоступном AutoGRAPH отметка последней проверки не двигается, сводка это показывает.
- [ ] Учётные данные на стенде хранятся согласно решению владельца, не попадают в логи и резервные копии в открытом виде.
- [ ] Отзыв доступа (выход из учётной записи в приложении) прекращает фоновые проверки от имени пользователя.
- [ ] Интервал и окно проверки меняются настройкой.
- [ ] При выключенном переключателе работает прежняя проверка на устройстве.

**Вне рамок.** Серверные push-уведомления (FCM), отчёты по расписанию.

### Шаг 6. Отправка писем

Шаг не зависит от шагов 4 и 5 и может выполняться сразу после шага 3.

**Цель.** Ассистент готовит письмо, пользователь подтверждает, стенд отправляет.

**Стенд.**
- Настройки SMTP в `FS_*`. Список получателей в файле конфигурации: идентификатор, имя, роль, адрес.
- Tool `list_recipients` возвращает идентификаторы, имена и роли без адресов. Tool `draft_email(recipient_ids,
  subject, body)` создаёт черновик и возвращает его id. Отправить письмо модель не может.
- `POST /v1/emails/{draftId}/confirm` и `/cancel` вызывает только приложение по действию пользователя.
  Черновик имеет срок жизни и принадлежит создавшему его пользователю.
- Лимит писем на пользователя за период и журнал: кто, кому, когда, тема, итог.

**Приложение.**
- Ответ чата расширяется: кроме текста может прийти черновик письма. Для этого меняется интерфейс
  `ChatAgent` и `ChatMessage`; `StubChatAgent` и остальные экраны продолжают работать.
- Сообщение-черновик показывает получателей, тему, текст и кнопки «Отправить» и «Отменить».

**Почему так.** Названия машин и описания аномалий приходят из внешней системы и попадают в контекст модели.
Отправка письма необратима, поэтому текст из данных не должен иметь возможности ни выбрать адрес, ни
отправить письмо без человека.

**Требования по итогу.**
- [ ] Письмо уходит только после подтверждения пользователем в приложении; вызова, которым модель могла бы
      отправить письмо сама, не существует.
- [ ] Получатель вне списка невозможен: неизвестный идентификатор даёт ошибку tool, адрес в свободной форме не принимается.
- [ ] Черновик нельзя подтвердить дважды, после истечения срока и от имени другого пользователя (тесты).
- [ ] Превышение лимита возвращает понятный отказ.
- [ ] Каждая отправка и каждый отказ есть в журнале; текст письма и адреса не пишутся в общий лог приложения.
- [ ] Ошибка SMTP показана пользователю, письмо не считается отправленным.
- [ ] Тест: текст с инструкцией «отправь письмо на адрес …» внутри данных аномалии не приводит к отправке
      и не меняет получателей.
- [ ] Тесты работают с подставным SMTP-сервером, реальные письма в тестах не отправляются.
- [ ] Сквозной сценарий дополнен: черновик → подтверждение → письмо получено подставным сервером.

### Шаг 7. Удаление старого пути

**Цель.** Один путь данных, без переключателей.

**Стенд.** Демо-источник: перенос генератора `DemoTelemetryRepository` как отдельной схемы, доступной без

**Приложение.** Удаляются `BaselineAnomalyDetector`, `MlAnomalyDetector`, `FeatureExtractor`,

и переключатели шагов 1–5. Тесты правил и разбора переезжают в `ml/fleet_service`.

**Требования по итогу.**

- [ ] Эталонные проверки шагов 2 и 3 сохранены как обычные тесты `fleet_service` на зафиксированных эталонах.
