# Устойчивость и защита от перегрузки: OpenRouter, AutoGRAPH, predictive_antifraud

Это задание для агента-разработчика, продолжение `assistant-server-plan.md`. Работа идёт по шагам 1–6.
После каждого шага приложение и стенд работают по полному циклу: пользователь открывает приложение,
видит данные, получает аномалии и ответ в чате. Шаг, после которого что-то из этого сломано, не считается
выполненным. Все новые настройки — в `Settings` (`FS_*` / `PA_*`) с описанием в `.env.example`.

---

## 1. О чём документ

Под «балансировкой нагрузки» здесь три разные задачи, и решаются они разными механизмами:

1. **Отказоустойчивость исходящих вызовов.** Провайдер модели, модель целиком или сам OpenRouter
   недоступны; AutoGRAPH или predictive_antifraud отвечают ошибкой. Механизмы: классификация ошибок,
   retry, fallback, circuit breaker, timeouts.
2. **Защита своих сервисов и чужих API от перегрузки.** Механизмы: лимиты конкурентности (bulkhead),
   ограниченные очереди и быстрый отказ (load shedding), rate limit на пользователя, кэш.
3. **Собственно load balancing** между репликами. Нужен, только когда одного инстанса перестанет хватать.
   Самая простая из трёх частей, но требует подготовки (раздел 5).

## 3. Чего не хватает

**LLM.**
- Все ошибки OpenRouter превращаются в один `LLMError` → 502. Не различаются ошибки, которые имеет смысл
  повторить (408, 429, 502, 503, сеть), и те, что повторять бесполезно (400, 401, 402, 403).
- Нет повторов и не учитывается заголовок `Retry-After`.
- Нет fallback на другую модель (массив `models` OpenRouter) и нет резерва на случай, когда недоступен сам
  OpenRouter (сеть со стенда, outage, кончились кредиты — 402).
- Нет circuit breaker: при лежащем OpenRouter каждый запрос честно ждёт `FS_LLM_TIMEOUT_SECONDS`.

**Перегрузка.**
- Нет лимита на пользователя для `/v1/chat`. Один ответ — до `FS_AGENT_MAX_ITERATIONS` обращений к модели
  плюс tools, то есть один запрос пользователя усиливается в разы.
- Нет общего предела одновременных чатов и общего предела вызовов AutoGRAPH и аналитики на процесс.
  `FS_SCAN_CONCURRENCY` ограничивает параллельность только внутри одного запроса scan: k одновременных
  запросов дают k × `FS_SCAN_CONCURRENCY` машин в работе, плюс фоновая проверка сверху.
- `predictive_antifraud`: обработчики `def` (синхронные), Starlette выполняет их в пуле потоков (по
  умолчанию 40). Явного предела и ограниченной очереди нет: при всплеске запросы копятся, задержка растёт
  неограниченно, а `fleet_service` по `FS_PREDICTIVE_TIMEOUT_SECONDS` уже ушёл, хотя расчёт продолжается.
- Пауза между повторами AutoGRAPH растёт линейно и без jitter: при массовом сбое все повторы приходят
  одновременно.
- `FS_TELEMETRY_CACHE_TTL_SECONDS` один для всех периодов, хотя закрытые периоды телеметрии не меняются.

## 4. Первые принципы, на которые опираются шаги

**Неограниченная очередь не защищает, а убивает.** Для простейшей модели M/M/1 время в системе
W = 1 / (μ − λ): при загрузке ρ = λ/μ → 1 задержка уходит в бесконечность, а не растёт плавно. Поэтому
перед каждым дорогим ресурсом — предел одновременных задач C и ограниченная очередь Q; когда очередь
полна, сразу отказ (429/503 с понятным текстом). Быстрый отказ лучше ответа через 3 минуты, когда
пользователь уже ушёл, а стенд всё ещё считает.

**Как выбрать C.** По закону Литтла L = λ·W: если расчёт идёт 2 с, а нужно держать 5 запросов в секунду,
в работе одновременно ~10 задач. Реальный потолок даёт только нагрузочный тест: поднимаем λ и смотрим,
где throughput перестаёт расти, а p95 latency начинает резко расти (knee point). C ставится чуть ниже.
Значения по умолчанию в шагах ниже — стартовые, их заменяют результаты теста.

**Повторы перемножаются.** Приложение повторяет 3 раза, стенд 3 раза, OpenRouter ещё перебирает
провайдеров — один запрос превращается в 9+ вызовов именно тогда, когда система перегружена (retry storm).
Правила: повторяет только один слой (стенд, в клиенте конкретного upstream); пауза — экспоненциальная с
jitter; доля повторов ограничена (retry budget).

**Повторять можно только идемпотентное.** Обращение к модели, чтение телеметрии, расчёт аналитики —
можно. Действие с побочным эффектом (отправка письма) — нет, если нет idempotency key. Сейчас письмо
отправляет подтверждение пользователя по черновику — это свойство нужно сохранить: повтор подтверждения
одного черновика не должен отправлять второе письмо.

## 5. Шаги

### Шаг 1. Классификация ошибок LLM, повторы, fallback модели

**Что сделать.**
1. В `agent/llm.py` разделить ошибки:
   - `LLMRetryable` — 408, 429, 502, 503, сетевые ошибки и timeout подключения;
   - `LLMCreditsExhausted` — 402 (кончились кредиты или лимит ключа). Не повторять, писать в лог уровнем
     ERROR — это повод для алерта;
   - `LLMError` — остальное (400, 401, 403): не повторять, это ошибка конфигурации или запроса.
2. Повторы `LLMRetryable` внутри `OpenRouterClient.complete`: до `FS_LLM_RETRIES` попыток, пауза
   `min(cap, base · 2^n) · random(0.5, 1)`; если есть `Retry-After` — ждать его, но не дольше остатка
   срока ответа чата (`FS_CHAT_TIMEOUT_SECONDS`). Повтор, который не успеет, не начинать.
3. Fallback модели: `FS_LLM_FALLBACK_MODELS` (список через запятую) → поле `models` запроса. В список
   попадают только модели, прошедшие проверку на наших tools (см. «Проверка» ниже). Модель, которая хуже
   следует JSON-схеме tools, — это деградация качества, а не надёжность.
4. Порядок провайдеров: `FS_OPENROUTER_PROVIDER_SORT` (`latency` | `throughput` | `price` | пусто) и
   `FS_OPENROUTER_ALLOW_FALLBACKS` (по умолчанию `true`). `require_parameters` остаётся `true`: иначе
   fallback может уйти к провайдеру, который молча игнорирует `tools`, и ассистент начнёт отвечать
   без данных.
5. Логировать, какая модель и провайдер фактически ответили (поля `model` и `provider` ответа), чтобы
   видеть долю fallback.

**Новые настройки.** `FS_LLM_RETRIES=2`, `FS_LLM_RETRY_BASE_SECONDS=1`, `FS_LLM_RETRY_MAX_SECONDS=10`,
`FS_LLM_FALLBACK_MODELS=`, `FS_OPENROUTER_PROVIDER_SORT=`, `FS_OPENROUTER_ALLOW_FALLBACKS=true`.

**Проверка модели для fallback.** Набор из 20–30 вопросов из реальных сценариев чата с ожидаемыми
вызовами tools (имя tool и ключевые аргументы). Модель допускается в `FS_LLM_FALLBACK_MODELS`, если
вызывает нужный tool с валидными аргументами не реже основной модели (допуск — по договорённости,
например −5 п. п.).

**Требования по итогу.**
- Тесты на каждый класс ошибок с подменённым HTTP (`httpx.MockTransport`): 429 с `Retry-After`
  повторяется, 402 и 400 не повторяются, повтор не выходит за срок ответа чата.
- Ответ чата при 402 — понятный текст «ассистент временно недоступен», в логе ERROR.
- Полный цикл в приложении работает с пустым `FS_LLM_FALLBACK_MODELS` (поведение как раньше).

### Шаг 2. Лимиты: пользователь, чат, внешние вызовы

**Что сделать.**
1. Rate limit на пользователя для `/v1/chat` (token bucket по логину и схеме): `FS_CHAT_RATE_PER_MINUTE`,
   `FS_CHAT_BURST`. Превышение — 429 с `Retry-After` и текстом для пользователя.
2. Общий предел одновременных ответов чата на процесс: `FS_CHAT_CONCURRENCY` и очередь
   `FS_CHAT_QUEUE_MAX`. Ожидание места в очереди входит в `FS_CHAT_TIMEOUT_SECONDS`. Очередь полна —
   сразу 503 «высокая нагрузка, повторите через минуту».
3. Общие семафоры на процесс для внешних вызовов, через которые идут **все** пути (чат, scan, фон):
   `FS_AUTOGRAPH_CONCURRENCY`, `FS_PREDICTIVE_CONCURRENCY`. Тогда суммарная нагрузка на AutoGRAPH и
   аналитику ограничена независимо от того, сколько запросов scan пришло одновременно.
4. Фоновая проверка уступает интерактивным запросам: она берёт место в семафоре только если в очереди
   нет ожидающих запросов пользователей (или получает свою долю, например не больше половины C).
5. Пауза повторов AutoGRAPH — экспоненциальная с jitter вместо линейной.

**Новые настройки (стартовые).** `FS_CHAT_RATE_PER_MINUTE=10`, `FS_CHAT_BURST=3`,
`FS_CHAT_CONCURRENCY=8`, `FS_CHAT_QUEUE_MAX=16`, `FS_AUTOGRAPH_CONCURRENCY=8`,
`FS_PREDICTIVE_CONCURRENCY=4`.

**Требования по итогу.**
- Тест: при `FS_CHAT_CONCURRENCY=1`, `FS_CHAT_QUEUE_MAX=1` третий одновременный запрос сразу получает 503.
- Тест: k одновременных scan не дают больше `FS_AUTOGRAPH_CONCURRENCY` одновременных вызовов AutoGRAPH.
- Приложение показывает пользователю текст 429/503 из `detail`, а не общую ошибку.

### Шаг 3. predictive_antifraud: предел и быстрый отказ

**Что сделать.**
1. Middleware или зависимость с семафором на тяжёлые эндпоинты (`/v1/predictive/analyze`,
   `/v1/antifraud/check`): `PA_MAX_CONCURRENCY` и `PA_QUEUE_MAX`, при переполнении — 503 с `Retry-After`.
   `/health` и `/ready` под предел не попадают.
2. `PA_REQUEST_DEADLINE_SECONDS` меньше `FS_PREDICTIVE_TIMEOUT_SECONDS`: запрос, простоявший в очереди
   дольше, не считается — клиент его уже не ждёт.
3. В `fleet_service` ответ 503 аналитики — `AnalyticsStatus(status="unavailable")` без повтора; правила
   работают как раньше.
4. Нагрузочный тест (`locust` или `k6`) на эндпоинт антифрода с реальным размером входа; по графику
   throughput / p95 выбрать `PA_MAX_CONCURRENCY`, записать результат в `predictive_antifraud/README.md`.

**Требования по итогу.**
- Тест на 503 при переполнении очереди.
- Записано значение `PA_MAX_CONCURRENCY` и как оно получено.

### Шаг 4. Circuit breaker и резерв на случай недоступного OpenRouter

**Что сделать.**
1. Circuit breaker на каждый upstream (OpenRouter, AutoGRAPH, predictive_antifraud): после
   `FS_BREAKER_FAILURES` ошибок за `FS_BREAKER_WINDOW_SECONDS` upstream считается недоступным на
   `FS_BREAKER_OPEN_SECONDS`; затем один пробный запрос (half-open). Пока breaker открыт — сразу ошибка
   или fallback без ожидания timeout. Ошибки 4xx клиента (кроме 408, 429) breaker не открывают.
2. Резервная модель вне OpenRouter: `FS_LLM_RESERVE_BASE_URL`, `FS_LLM_RESERVE_MODEL`,
   `FS_LLM_RESERVE_API_KEY` — любой OpenAI-совместимый endpoint (свой vLLM или прокси LiteLLM). Переход на
   резерв: breaker OpenRouter открыт, 402, или исчерпаны повторы. Пустой адрес — резерва нет.
3. Резервная модель проходит ту же проверку на tools, что и в шаге 1. Если её качество ниже — ассистент
   добавляет к ответу пометку, что работает в упрощённом режиме (без изменения цифр: их всё равно считают
   tools).
4. Состояние breaker'ов — в `/health` (подробно — в отдельном `/v1/status` для администратора).

**Альтернатива.** Вынести шаги 1 и 4 для LLM в прокси LiteLLM на стенде (fallbacks, retries, cooldown
провайдеров уже есть), а `fleet_service` ходит только в него. Плюс — меньше своего кода; минус — ещё
один контейнер и своя конфигурация. Решение фиксируется до начала шага.

**Требования по итогу.**
- Тест: после N ошибок breaker открыт, следующий вызов не делает HTTP-запроса; через `OPEN_SECONDS` —
  один пробный.
- Ручная проверка: неверный `FS_OPENROUTER_BASE_URL` при заданном резерве — чат отвечает через резерв.

### Шаг 5. Кэш по смыслу данных

**Что сделать.**
1. Разные TTL для телеметрии: период целиком в прошлом (конец периода раньше «сейчас − задержка
   поступления данных») — `FS_TELEMETRY_CLOSED_CACHE_TTL_SECONDS` (часы); период, захватывающий «сейчас», —
   текущий `FS_TELEMETRY_CACHE_TTL_SECONDS`. Задержку поступления данных взять из наблюдений за AutoGRAPH
   и вынести в `FS_TELEMETRY_SETTLE_MINUTES`.
2. Кэшировать результат аналитики по `(схема, машина, период, версия модели)` с теми же правилами.
3. Предел памяти кэша — по числу записей, как сейчас; размер одной записи логировать при загрузке, чтобы
   выбрать `*_MAX_ENTRIES` по данным.

**Требования по итогу.**
- Тест: закрытый период живёт в кэше дольше открытого.
- Повторный вопрос в чате о прошлой неделе не вызывает AutoGRAPH (видно в логе).

### Шаг 6. Наблюдаемость и подготовка к репликам

**Что сделать.**
1. Метрики Prometheus (`prometheus-fastapi-instrumentator` + свои счётчики): ошибки по upstream и коду,
   длительность по upstream (p50/p95), доля ответов через fallback-модель и резерв, состояние breaker'ов,
   глубина очередей и число отказов 429/503 по причине, попадания в кэш.
2. Подготовка к нескольким репликам `fleet_service`. Сейчас один процесс uvicorn, и состояние в памяти
   (кэши, лимиты, breaker'ы, планировщик) согласовано. При репликах:
   - rate limit и лимиты писем — в Redis, иначе лимит «10 в минуту» на трёх репликах станет 30;
   - кэш — Redis или остаётся локальным (допустимо: хуже hit rate, но корректно);
   - фоновая проверка — только на одной реплике (блокировка в Redis или в БД);
   - SQLite заменить на PostgreSQL;
   - перед репликами — nginx/Traefik со стратегией least connections: ответы чата длятся от секунд до
     минуты, round-robin даёт неравномерную нагрузку.
   Делается, когда метрики покажут, что одного процесса не хватает. До этого — только записать решение.

**Требования по итогу.**
- Дашборд с метриками выше; алерты на 402 OpenRouter, открытый breaker дольше 5 минут, долю 503 > 5 %.

## 7. Справка по OpenRouter

- Провайдеры одной модели перебираются автоматически (`provider.allow_fallbacks`, по умолчанию `true`);
  порядок — `provider.order` / `provider.sort`, ограничение — `provider.only` / `provider.ignore`.
  Каждое ограничение сокращает число вариантов для восстановления.
- Другая модель при отказе — только явно, массивом `models`; переход вызывает любая ошибка, включая
  превышение длины контекста.
- Коды: 401 ключ, 402 кредиты или лимит ключа, 403 модерация/guardrail, 408 timeout, 429 rate limit,
  502 модель недоступна или ответ невалиден, 503 нет провайдера под требования маршрутизации.
  На 429 и 503 может прийти `Retry-After`.
- Лимиты считаются глобально: новые ключи и аккаунты их не увеличивают.

Источники: [Errors and debugging](https://openrouter.ai/docs/api-reference/errors-and-debugging),
[Limits](https://openrouter.ai/docs/api-reference/limits),
[Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection),
