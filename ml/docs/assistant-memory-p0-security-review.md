# P0: контракт идентичности и проверка безопасности

Дата: 20.11.2026. Проверяется код и изолированный тестовый стенд, а не рабочее развёртывание.

## Выбранная модель: stand_bound с управляемым реестром

В P0 используется собственный неизменный UUID пользователя и отдельный реестр `identity_accounts`.
AutoGRAPH Login подтверждает владение точным логином и паролем; EnumSchemas отдельно подтверждает
актуальный доступ к схеме. Токен сессии и `X-User-Name` не являются долговременной личностью.
`provider_subject` — внутренний идентификатор реестра, не заявленный UID AutoGRAPH.

Официальная документация описывает `User.UID`, но просмотренное описание не даёт подтверждённого
метода ServiceJSON для получения UID по используемой сессии. Такой метод не придуман и не проверялся
на рабочем сервере: [интерфейс пользователя в документации плагинов](https://docs.tk-nav.ru/web/docs/development/plugins/plugins/),
[общее описание API](https://docs.tk-nav.ru/web/docs/development/API/api/).

Резервный контракт P0 требует управляемого жизненного цикла:

- Логин не передаётся другому человеку, пока прежняя личность не выведена из обращения через `retire`.
- Переименование выполняется согласованно в AutoGRAPH и реестре через `rename`; UUID сохраняется,
  прежние credentials и персональные Telegram-привязки отзываются.
- `retire` отключает прежний UUID во всех схемах, отзывает credentials и Telegram, освобождает логин.
  Повторный Login на этот логин создаёт новый UUID; старые сведения ему не доступны.
- На время изменений оператор выключает `FS_IDENTITY_ENABLED`, не допускает входов между изменением
  AutoGRAPH и реестра и включает API после проверки согласованности.
- Прямое изменение/повторная выдача логинов в обход этого процесса не поддерживается. Если такой
  процесс организационно не обеспечивается, персональный API должен оставаться выключенным.

Это явное условие безопасности, а не утверждение о фактически принятом регламенте рабочей установки.
Условие подтверждается оператором через `FS_IDENTITY_ACCOUNT_LIFECYCLE=managed`.
По умолчанию установлены `FS_IDENTITY_ENABLED=false` и `FS_IDENTITY_ACCOUNT_LIFECYCLE=unconfigured`;
одного включения первого флага недостаточно. Клиент или модель изменить эти настройки не могут.
Подключение нативного AutoGRAPH UID — возможный отдельный адаптер, когда появится проверенный контракт.

## Полномочия и границы

| Операция | Доказательство | Поведение при отказе |
| --- | --- | --- |
| bind приложения | Явное согласие, серверный Login, текущая схема, управляемый реестр | Нет principal/credential при ошибке |
| личный API приложения | Хэш credential, исходная проверенная сессия, схема, активные principal/scope; свежий EnumSchemas | 401/403; при недоступном AutoGRAPH — 503 без fallback |
| отзыв | Исходная пара credential/сессия и схема, проверяемые локально | Чужая/неизвестная пара — тот же 204 без изменений |
| код Telegram | Ключ доверенного бота, реальный private chat/user из Telegram; chat_id=user_id>0 | Группы и несовпадающий user_id не поддерживаются |
| подтверждение Telegram | Отдельное согласие и одноразовый код в проверенной сессии приложения | Код нельзя погасить повторно/после истечения |
| личный API Telegram | Личная привязка и активный исходный credential, зашифрованная исходная сессия, свежий EnumSchemas | Старое подключение по username не даёт полномочий |
| rename/retire | Только оператор с доступом к БД; команды отсутствуют в API и tools модели | По умолчанию проверка без записи, применение через `--apply` |

Telegram не получает секреты приложения. Сервер хранит его сессию только в AES-GCM шифротексте
с AAD по chat/user/tenant/credential. Ключ — существующий `FS_ACCESS_ENCRYPTION_KEY`. Срок Telegram
не длиннее исходного credential (один час). Отзыв, отключение principal/scope, истечение сессии и
прав закрывают доступ. После переподключения старого бота личный профиль инвалидируется.
Подмена username в старом app-unlink не может удалить активный личный профиль: требуется сначала
отключить его через проверенный API или из личного чата командой `/forget_identity`.

История/числа/aliases в LLM ещё не передаются; `/v1/chat` не получает личность автоматически.
Будущие личные инструменты должны использовать доверенный Principal вместе с его проверенной
сессией и повторно проверять доступные машины. Слияние сессии одного пользователя и principal другого запрещено.

## Android

Пара credential/сессия хранится только как AES-256-GCM шифротекст в SettingsRepository; ключ —
Android Keystore. Смена логина/пароля/схемы/стенда атомарно увеличивает поколение и выключает старую
пару. Возврат к прежним значениям её не восстанавливает. Согласие на bind/pair относится к конкретному
поколению и credential: пароль/код не пересылаются по новым настройкам после гонки изменений.

Отключение сначала сохраняет намерение отзыва, затем обращается к сети. Повтор выполняется при
работающем приложении и после запуска; при недоступном стенде не показывается подтверждение отзыва.
Локальное удаление без подтверждённого отзыва — отдельное действие с предупреждением о сроке доступа.
Обновления по сохранённому паролю для личного API нет. Редиректы и повтор Login отключены;
release требует HTTPS, debug дополнительно разрешает loopback HTTP для fakes.

Backup/device-transfer DataStore исключён существующими XML-правилами; ключ Keystore не экспортируется.
Повреждение шифротекста или отсутствие исходного ключа закрывают профиль. Проверка Android проводится
отдельным пакетом `.p0test`, с локальными URL и тестовым runner, который отказывается запускаться
в обычном приложении. Все данные и пользователи синтетические.

## Проверки и оставшиеся эксплуатационные условия

Результаты автоматических, инструментальных и UI-проверок фиксируются в
[плане реализации](petrovich_assistant_memory_implementation_plan.md). Рабочие аккаунты,
AutoGRAPH, Telegram, SMTP и LLM не вызывались. Рабочая конфигурация не включалась.

Рабочее включение отдельно требует принятого оператором регламента managed, HTTPS и защиты Login
на ingress. Это не разрешение на развёртывание и не подтверждение внешней политики провайдера.
До этого оба флага должны оставаться в безопасном исходном состоянии.

## Миграция и откат

Миграция `0010` добавляет реестр/аудит жизненного цикла и отдельные коды/привязки Telegram.
Переход с `0009` сохраняет существующие UUID. Перед обновлением нужна согласованная копия SQLite.
Откат на `0009` удаляет новые привязки, отзывает credentials и восстанавливает совместимые ключи
активных аккаунтов; повторный вход нужен, UUID активных аккаунтов сохраняются. Данные обычного
чата, аномалий и писем не меняются. Восстановление старой резервной копии может вернуть прежние
credentials; перед открытием личного API они должны быть отозваны оператором.
