# Предиктивная аналитика и антифрод

FastAPI-сервис для «Петрович Телеметрия». Принимает телеметрию одной машины за период в том же виде, что
`VehicleTelemetry` в приложении, и возвращает аномалии в формате `Anomaly` (id стабилен — приложение
дедуплицирует по нему).

- **Предиктивная аналитика** (`POST /v1/predictive/analyze`) — признаки деградации двигателя, охлаждения, АКБ до отказа.
- **Антифрод** (`POST /v1/antifraud/check`) — сливы и фиктивные заправки топлива, расход, не согласующийся с пробегом.

Пока модели не обучены, сервис работает и отвечает `{"ready": false, "anomalies": []}` — как `isReady = false`
у `MlAnomalyDetector`.

## Запуск

```bash
cd ml/predictive_antifraud
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt          # или pip install -e ".[dev]"
uvicorn predictive_antifraud.main:app --app-dir src --reload     # http://127.0.0.1:8000/docs
pytest
```

Docker: `docker build -t petrovich-pa . && docker run -p 8000:8000 -v $PWD/models:/srv/models petrovich-pa`.

Настройки — переменные окружения с префиксом `PA_` (см. `.env.example`).

## Эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | liveness |
| GET | `/ready` | какие модели загружены |
| POST | `/v1/predictive/analyze` | предиктивная аналитика |
| POST | `/v1/antifraud/check` | антифрод |

При заданном `PA_API_KEY` эндпоинты `/v1/*` требуют заголовок `X-API-Key`.

## Нагрузка

Обработчики `/v1/*` синхронные и идут в пуле потоков Starlette (40 потоков). Без предела при всплеске запросы
копятся, задержка растёт без границы, а расчёт продолжается после того, как стенд по
`FS_PREDICTIVE_TIMEOUT_SECONDS` уже ушёл. Поэтому (`api/limits.py`):

- одновременно в расчёте не больше `PA_MAX_CONCURRENCY` запросов, в очереди — не больше `PA_QUEUE_MAX`; очередь
  полна — сразу `503` с `Retry-After: 5`;
- запрос, простоявший в очереди дольше `PA_REQUEST_DEADLINE_SECONDS`, не считается (`503`); держите его меньше
  `FS_PREDICTIVE_TIMEOUT_SECONDS` стенда;
- `/health` и `/ready` под предел не попадают.

Стенд получает `503` как статус аналитики `unavailable` («сервис аналитики перегружен»), без повтора; проверка по
правилам работает как обычно.

**Как выбрано `PA_MAX_CONCURRENCY=2`.** Нагрузочный тест `scripts/load_test.py` ступенями поднимает число
одновременных запросов к `/v1/antifraud/check`. Вход — `VehicleTelemetry` за 7 дней по 15 мин (673 строки, 13
столбцов, 112 КБ) из `testdata/golden/trip-tables/synthetic-7d.case.json`, как его собирает приложение. Предел на
время теста снят. Прогон 2026-10-23 на машине разработки (4 ядра, 8 ГБ, один процесс uvicorn, Python 3.14), по 8 с
на ступень:

| Одновременно | С моделью-заглушкой (`--stub-model`): запросов/с · p50 · p95, мс | Без модели (`ready: false`): запросов/с · p50 · p95, мс |
|---|---|---|
| 1 | 146 · 5 · 17 | 182 · 4 · 11 |
| 2 | 130 · 12 · 38 | 196 · 8 · 30 |
| 4 | 107 · 33 · 70 | 212 · 15 · 43 |
| 8 | 99 · 78 · 131 | 231 · 29 · 65 |
| 16 | 97 · 159 · 250 | 218 · 71 · 116 |
| 32 | 97 · 324 · 462 | 231 · 131 · 245 |

С расчётом признаков throughput не растёт уже после одного запроса и дальше падает (расчёт упирается в один
процесс Python), а p95 удваивается на каждой ступени; без модели прирост throughput после 2 — в пределах шума при
том же росте p95. Колено около 2, предел поставлен на нём. Это **предварительное** значение:
модели пока нет, заглушка только извлекает признаки. С появлением модели (и на сервере стенда, а не машине
разработки) тест нужно повторить:

```bash
.venv/bin/python scripts/load_test.py --stub-model                     # расчёт с заглушкой модели
# работающий сервис — запущенный с PA_MAX_CONCURRENCY=1000 и PA_QUEUE_MAX=1000, иначе таблица покажет очередь
# текущего предела, а не мощность
.venv/bin/python scripts/load_test.py --url http://127.0.0.1:8001 --api-key "$PA_API_KEY"
```

Стенд держит свой предел `FS_PREDICTIVE_CONCURRENCY` не больше этого (по умолчанию тоже 2): тогда запросы ждут на
стенде, где запросы пользователей идут вперёд фоновой проверки, а не в простой очереди аналитики. Стенд передаёт
остаток своего срока в заголовке `X-Client-Timeout`: дольше него запрос в очереди аналитики не ждёт.

Если расчёт станет тяжелее и будет отпускать GIL (onnxruntime, numpy), колено сдвинется вправо; если упрётся в
один процесс — масштабировать числом процессов uvicorn (`--workers`), а не пределом (предел действует в каждом
процессе отдельно).

## Структура

```
src/predictive_antifraud/
  main.py              create_app(), загрузка моделей в lifespan
  config.py            настройки (PA_*)
  api/                 роуты и зависимости
  schemas/             VehicleTelemetry (вход), Anomaly / DetectionResponse (выход)
  features/            матрица признаков время × параметры, имена параметров AutoGRAPH
  models/              интерфейс ScoringModel и реестр моделей
  services/            признаки → оценки → эпизоды → Anomaly; профили predictive / antifraud
models/                артефакты моделей (не коммитятся)
tests/
```

## Особенности данных AutoGRAPH

- При выключенном зажигании (`DIgnition` / `DIgnitionCAN`) CAN-параметры приходят нулями, а обороты `Rotation`
  «замирают». `features/extractor.py` считает такие значения пропусками и отдаёт маску `observed`.
- `BattaryVOLTAGE` есть только у Урал NEXT. `FeatureMatrix.reindex()` дополняет отсутствующие столбцы нулями
  с `observed = False`, чтобы у модели был фиксированный набор признаков.
- Соседние строки над порогом объединяются в один эпизод. id = `ml|<predict|fraud>|<vehicleId>|<параметр>|<начало эпизода>`,
  поэтому повторные сканы (окно 3 ч каждые 15 мин) не плодят дубликаты.

## Как подключить модель

1. Положить артефакт в `models/predictive.*` или `models/antifraud.*`.
2. Добавить рантайм (onnxruntime / scikit-learn / lightgbm) в `pyproject.toml`.
3. Реализовать загрузку в `models/registry.py::load_model` — объект с интерфейсом `ScoringModel`
   (`version`, `expected_features`, `score(FeatureMatrix) -> оценки 0..1 по строкам`).
