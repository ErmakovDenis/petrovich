# Ручная проверка приложения со стендом

Порядок проверки приложения на реальных данных AutoGRAPH и реальной модели через стенд `ml/fleet_service`
(состояние плана — шаг 6). Выполняет человек: реальные ключи, учётные данные и устройство в автоматические
проверки не попадают. Секреты (`.env`, токены, пароль) никуда не пересылать — ни в чат, ни в задачи.

## 0. Автоматические проверки

```bash
.claude/skills/fleet-check/check.sh     # gradle testDebugUnitTest + assembleDebug, оба pytest, smoke.sh
```

`smoke.sh` гоняет стенд через compose с подставными OpenRouter, GigaChat и AutoGRAPH. Пока здесь есть красное — на устройство
не идти.

## 1. Настройки стенда (`.env`)

```bash
cd ml
cp fleet_service/.env.example fleet_service/.env
cp predictive_antifraud/.env.example predictive_antifraud/.env
```

- `fleet_service/.env`: `FS_LLM_PROVIDER` и настройки этого режима (`DEPLOY.md`, п. 4.2): `FS_GIGACHAT_CREDENTIALS`,
  `FS_GIGACHAT_CA_BUNDLE` или `FS_OPENROUTER_API_KEY`, `FS_LLM_MODEL`; `FS_PREDICTIVE_API_KEY`; для фоновой проверки —
  `FS_ACCESS_ENCRYPTION_KEY` (`python3 -c "import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"`).
- письма — в `fleet_service/.env` `FS_SMTP_HOST`, `FS_SMTP_PORT`, `FS_SMTP_SECURITY`, `FS_SMTP_USERNAME`,
  `FS_SMTP_PASSWORD`, `FS_SMTP_FROM` и `FS_EMAIL_RECIPIENTS_PATH=/srv/config/recipients.toml`; получатели —
  `cp fleet_service/config/recipients.example.toml fleet_service/config/recipients.toml`, для первой проверки —
  только свой адрес.
- `predictive_antifraud/.env`: `PA_API_KEY` — то же значение, что `FS_PREDICTIVE_API_KEY`.

Ключ аналитики — общий секрет двух сервисов, его придумывают сами:

```bash
openssl rand -hex 32     # или: python3 -c "import secrets; print(secrets.token_hex(32))"
```

Пустые оба — проверка `X-API-Key` отключена (только для локальной разработки: в compose аналитика открыта на порту
хоста 8001). Разные значения — аналитика отвечает стенду 401; проверка правилами при этом работает, а поле
`analytics` в ответе `/v1/anomalies/check` показывает ошибку.

Остальные `FS_*` можно оставить по умолчанию; хранилище аномалий (SQLite) лежит в томе compose `fleet_data`.

## 2. Запуск стенда и проверка без приложения

```bash
docker compose up -d --build                                             # fleet_service :8080, predictive_antifraud :8001
curl -s localhost:8080/health          # {"status":"ok","llmProvider":"gigachat","llmConfigured":true,"backgroundConfigured":true,"emailConfigured":true,...}
curl -s localhost:8001/health
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/v1/vehicles      # 401 — без токена стенд не отвечает
```

`llmConfigured: false` — не заданы ключ или модель активного режима; `backgroundConfigured: false` —
не задан `FS_ACCESS_ENCRYPTION_KEY`; `emailConfigured: false` — не заданы SMTP, отправитель или файл получателей.

## 3. Сборка и установка debug-APK

```bash
source scripts/env.sh && ./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Связь телефона со стендом:

- по USB (проще): `adb reverse tcp:8080 tcp:8080`, адрес в приложении — `http://127.0.0.1:8080`;
- по Wi-Fi: адрес `http://<IP ПК>:8080`, телефон и ПК в одной сети, порт 8080 открыт в файрволе.

HTTP без TLS разрешён только в debug-сборке; release ходит на стенд только по HTTPS.

## 4. Базовая линия — старый путь

1. Онбординг: реальные данные (не демо), свой логин AutoGRAPH.
2. Все переключатели стенда выключены.
3. Запомнить (лучше скриншотами), что показывают для 1–2 машин за 6 ч и 24 ч: «Главная» (плитки статуса парка,
   «Сводка»), «Таблицы» и «Графики» (карточки внизу «Главной»), карточка машины во вкладке «Парк».
4. Вкладка «Проблемы» → «Проверить сейчас» (значок поиска в заголовке) — запомнить найденные аномалии.

С этим сравниваются следующие шаги.

## 5. Переключатели — по одному

Вкладка «Настройки» → «Ещё» → «Подключение и данные». Раздел «Стенд» → «Адрес стенда» → «Сохранить адрес». Дальше
включать по одному (переключатели раздела «Аномалии» — ниже на том же экране) и проверять:

| Переключатель | Что проверить |
|---|---|
| «Данные через стенд» | Таблицы, графики, «Главная», карточка машины и карточка аномалии по тем же машинам и периодам совпадают с базовой линией; список во вкладке «Проблемы» не сбросился |
| «Ассистент через стенд» | «Какие у меня машины?», «Проверь <машина> за сутки» — числа в ответах совпадают с таблицами; чат из карточки аномалии знает, о какой аномалии речь |
| «Аномалии со стенда» (раздел «Аномалии») | «Проблемы» → «Проверить сейчас» находит то же, что на устройстве. В debug — «Сравнивать с устройством (отладка)» и `adb logcat -s AnomalyCompare`: расхождений нет |
| «Хранить аномалии на стенде» (вместе с «Аномалиями со стенда») | Список «Проблемы» и карточка приходят со стенда, локальная история перенеслась (отчёт — под переключателем); решения — «Ложная» в карточке или «Разберись» → «Закрыть разбор» — переживают перезапуск приложения; второй телефон или пользователь той же схемы видит те же решения; новые события дают пуш, повторная проверка не плодит дубли |
| «Фоновая проверка на стенде» (вместе с «Хранить аномалии на стенде») | Под переключателем — «Доступ стенда: сессия AutoGRAPH», интервал и время последней проверки; в логе стенда раз в 15 мин `фоновая проверка: схема …`. Закрыть приложение (смахнуть из недавних) и не открывать: новая аномалия приходит пушем, во вкладке «Проблемы» и в истории уведомлений (колокольчик на «Главной») — после открытия. Второй телефон с тем же логином: пуш только на одном |
| «Письма из чата» (вместе с «Ассистентом через стенд») | Вкладка «Петрович»: «Подготовь письмо механику о <аномалия>» — в чате черновик «ЧЕРНОВИК ПИСЬМА · СТЕНД»: получатель из списка с адресом, тема, текст с числами из данных, «Отправить» / «Отменить». До нажатия письма нет. «Отправить» — письмо пришло на адрес из списка, в черновике «Отправлено»; второй раз кнопки нет. «Отменить» на другом черновике — письмо не приходит. «Напиши на адрес кто-то@пример.рф» — ассистент отвечает, что так нельзя. Ответ модели не утверждает, что письмо отправлено, пока вы не нажали «Отправить». Без «Ассистента через стенд» письма готовит локальный Петрович — его черновик открывается в почтовом клиенте телефона, стенд не участвует |
| «Разрешить стенду входить самостоятельно» | Под переключателем — «… и сохранённый пароль». Телефон в режим полёта на несколько часов: в логе стенда `стенд вошёл в AutoGRAPH по сохранённому паролю`, проверки идут. Выключить — «сохранённый пароль» пропадает из статуса |

## 6. Отказы и откат

- `docker compose stop fleet_service` — приложение показывает понятную ошибку на русском и не падает;
  после `docker compose start fleet_service` всё восстанавливается.
- Фоновая проверка на стенде, AutoGRAPH недоступен (например, на ПК со стендом заблокировать адрес AutoGRAPH в
  файрволе): через ~45 мин на «Главной» появляется карточка «Стенд давно не проверял данные», время последней проверки (под
  переключателем «Фоновая проверка на стенде») не двигается.
- Выключить «Фоновую проверку на стенде» (или включить демо-режим): в логе стенда больше нет проверок от имени
  устройства; `GET /v1/background/access?deviceId=…` — `registered: false`.
- Письма: неверный `FS_SMTP_PASSWORD` — «Отправить» показывает «Письмо не отправлено: почтовый сервер не принял логин
  стенда», черновик можно отправить снова после исправления. Подождать срок черновика (30 мин) — «Срок черновика
  истёк». Журнал: `docker compose exec fleet_service python -c "import sqlite3; [print(r) for r in
  sqlite3.connect('/srv/data/fleet.db').execute('select at, user_name, recipients, subject, outcome, error from
  email_log order by id desc limit 10')]"` — каждая отправка и отказ, без адресов и текста.
- Все переключатели выключены — старый путь работает как в п. 4.

## 6а. Срок жизни токена сессии (для решения о фоновой проверке без пароля)

Включить «Фоновую проверку на стенде» без согласия на пароль, телефон — в режим полёта. Когда токен истечёт, в
логе стенда появится `токен устройства … истёк, стенд знал его N ч`:

```bash
docker compose logs fleet_service | grep 'истёк, стенд знал'
```

N — нижняя оценка срока жизни токена (от последней выдачи стенду до первого отказа; точность — интервал проверки).

## 7. Логи стенда без секретов

```bash
docker compose logs fleet_service gigachat_gateway | grep -iE 'session=|bearer|basic |access_token|password=|sk-or'
docker compose logs fleet_service | grep -c '<адрес получателя>'     # 0: адреса и текст письма в лог не пишутся
```

После каждого маркера — только `***`. В базе токены и пароль — только шифротекстом:

```bash
docker compose exec fleet_service sh -c 'cat /srv/data/fleet.db*' | grep -ac '<свой пароль>'   # 0
```

## 8. Режим GigaChat на настоящем API (шаг 5 плана `docs/gigachat-plan.md`)

Выполняет человек, запросы тратят токены. Автоматические проверки этого не покрывают: `eval_cases.jsonl` смотрит только
первый вызов tool, а подставной GigaChat не показывает качество ответов.

**Подготовка.** Ключ и сертификат в `.env` (`DEPLOY.md`, п. 4.2), режим пока `openrouter`. Шлюз поднялся:
`docker compose ps gigachat_gateway` — healthy.

**8.1. Набор проверки на tools, сравнение с текущей моделью.**

```bash
docker compose exec -e FS_EVAL_API_KEY=test fleet_service python -m fleet_service.agent.eval_tools \
    --base-url http://gigachat_gateway:8000/v1 --model GigaChat-2-Pro --model GigaChat-2-Max --repeat 3
```

Текущую модель — той же командой с адресом OpenRouter и его ключом. Требование плана: доля «tool и аргументы» не ниже
текущей модели минус 5 п. п.

**8.2. Сверка с настоящим API.** Записать результат каждого пункта:

- вид `arguments`: второе обращение цепочки не получает 422. Если получает — `FS_GIGACHAT_ARGUMENTS_FORMAT=string`;
- адрес `FS_GIGACHAT_BASE_URL` работает;
- модели-кандидаты доступны на тарифе `PERS` и умеют функции (иначе 422 в логе шлюза);
- срок токена в логе шлюза `получен токен доступа, осталось N с` — около 1800, а не тысячи лет;
- запрос без `functions_state_id` в истории принимается (нужно для шага с резервом посреди ответа и для набора 8.1).

**8.3. Ручной сценарий.** Переключить: `FS_LLM_PROVIDER=gigachat`, `docker compose up -d --wait`, в чате приложения задать
вопросы. Для каждого записать: какие tools вызваны, совпали ли числа, сколько секунд занял ответ. Вызовы и время — в логе:

```bash
docker compose logs fleet_service | grep -E 'модель вызывает tool|чат: схема'
# итерация 1: модель вызывает tool list_vehicles(...) ; чат: схема …, обращений к модели 3 (primary, primary, primary), tools […], 12.3 с
```

| Вопрос | Что проверить |
|---|---|
| «Сколько топлива у <машина> за сутки?» | Цепочка из двух tools: `list_vehicles`, затем `get_vehicle_summary` |
| «Есть ли аномалии у <машина> за неделю?» | `check_vehicle`; статус предиктивной проверки назван честно |
| «Сравни расход топлива <машина 1> и <машина 2> за неделю» | Цепочка из трёх и более tools: укладывается ли в `FS_AGENT_MAX_ITERATIONS` (5) и в срок ответа |
| «Какие аномалии были вчера? Что решили по последней?» | `list_anomalies`, затем `get_anomaly` |
| Чат из карточки аномалии: «Что случилось и что делать?» | Контекст аномалии учтён, в ответе нет выдуманных чисел |
| «Подготовь письмо механику о перегреве» | `list_recipients`, затем `draft_email`; письмо уходит только после подтверждения |
| То же в Telegram-боте | Ответы и черновики работают без изменений в боте |

**Числа.** Результаты tools в лог не пишутся: сверяйте числа из ответа с данными за тот же период. Топливо и параметры — на
экранах «Таблицы» и «Графики» приложения или в `GET /v1/telemetry`, аномалии — в `POST /v1/anomalies/check` и в ленте.
Ответ без вызова tool при вопросе о данных (в логе нет `модель вызывает tool`) — сбой: `tool_choice: required` в этом режиме
недоступен, и модель может отвечать сама.

**Вопросы про сливы топлива.** Задать 5–10 обычных вопросов: «Был ли слив топлива у <машина> вчера?», «Покажи сливы за
неделю», «Как понять, что топливо сливают?». Обычный вопрос не должен получать отказ по теме:

```bash
docker compose logs gigachat_gateway | grep -c 'blacklist'     # 0
```

Если отказы есть, переключать ли режим, решает владелец.

**Время.** Ответы укладываются в `FS_CHAT_TIMEOUT_SECONDS` (100 с): последнее число в строке `чат: …`. p95 не считается: нет
инструмента, выборка мала (`docs/assistant-eval.md`). Два одновременных вопроса с разных устройств идут по очереди, второй дольше.

**Откат.** `FS_LLM_PROVIDER=openrouter`, `docker compose up -d --wait`; в логе после вопроса — `режим openrouter`, чат отвечает.

## Если что-то не так

Собрать для разбора:

- пункт проверки, что ожидалось и что получилось;
- фрагмент `docker compose logs fleet_service` (маскируется автоматически, но перед отправкой просмотреть глазами);
- `adb logcat` с ошибкой.

## Куда уходит токен сессии AutoGRAPH

Для справки при проверке логов и трафика:

- приложение получает токен через `Login` и держит его только в памяти; логин и пароль — в DataStore на устройстве;
- на стенд токен уходит в `Authorization: Bearer`, вместе с `X-Schema-Id` и `X-User-Name` (логин без пароля);
- стенд проверяет токен через `EnumSchemas` (кэш — по SHA-256 токена) и передаёт его в AutoGRAPH как `session=`;
- с «Фоновой проверкой на стенде» стенд хранит последний токен устройства в базе зашифрованным
  (`FS_ACCESS_ENCRYPTION_KEY`); пароль — только с «Разрешить стенду входить самостоятельно», тоже зашифрованным;
  выключение переключателя удаляет оба;
- в модель (OpenRouter, GigaChat), `predictive_antifraud` и таблицы аномалий токен не попадает.
