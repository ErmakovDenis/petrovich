# Инструкции для работы с «Петрович Телеметрия»

## Начало работы

- Общайся с пользователем по-русски. Перед изменениями прочитай относящиеся к задаче исходники и документацию.
- Новые комментарии в коде, пользовательские тексты и описания изменений пиши по-русски.
- Начни с `git status --short`; сохраняй чужие изменения и незакоммиченные файлы.
- Карта проекта и порядок чтения: [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). Для Android дополнительно действуют `app/AGENTS.md`, для серверов — `ml/AGENTS.md`.
- Текущее поведение проверяй по коду и тестам. Планы в `ml/docs/` содержат описание состояния на момент написания и не являются достоверным списком оставшихся задач.
- Меняй только необходимое для задачи. Не выполняй коммит, push, развёртывание или обращения к настоящим платным моделям без соответствующего поручения.

## Основные ограничения

- Сохраняй локальный путь Android, демо-режим и переключатели стенда. Их удаление — отдельный шаг 7 плана, а не попутный рефакторинг.
- Контракты Kotlin и Python должны совпадать: JSON camelCase, схемы `VehicleTelemetry` и `Anomaly`, фикстуры `testdata/contract/`.
- Сохраняй совпадение маппинга телеметрии и правил между Android и сервером; проверяй общие эталоны `testdata/golden/` с обеих сторон.
- Время телеметрии — местное время пользователя без зоны, смещение приходит через `utcOffsetMinutes`/`UTCOffset`. Каноническая сетка хранилища и UTC в идентификаторах событий — отдельная логика; не подменяй её локальным временем машины разработчика.
- Ноль, отсутствующий датчик и отсутствие данных различаются. При выключенном зажигании CAN может возвращать нули, а обороты — последнее значение. Не упрощай фильтрацию и агрегацию.
- Ассистент получает факты и числа из tools. Не подменяй недоступную аналитику утверждением об отсутствии проблем. Письма отправляются после явного подтверждения пользователя в приложении или боте.
- Секреты не должны попадать в код, APK, документацию и логи. В AutoGRAPH секреты бывают в query-строке. Для разработки используй `.env.example` и подставные серверы тестов.
- Новые настройки документируй в соответствующем `.env.example`; при изменении поведения обновляй относящийся к нему README.

## Проверки и отчёт

- Запускай проверки затронутого компонента; при изменении общего контракта, агрегации или правил проверяй Android и Python.
- Для завершённого шага серверного плана предусмотрены Android unit-тесты и сборка, pytest обоих серверов и бота, проверка алертов через promtool и smoke-сценарий. Команды и требования окружения — во вложенных AGENTS.md.
- Для изменений только документации достаточно проверить ссылки, пути и diff. Не устанавливай зависимости ради такой проверки.
- В результате укажи созданные/изменённые файлы, выполненные проверки и ограничения. Не называй незапущенные тесты пройденными.
- При завершении шага плана сверяй каждый пункт «Требований по итогу» с конкретным тестом, командой или ручной проверкой. Указывай новые настройки, отступления и найденные проблемы вне шага; не начинай следующий шаг без поручения. Формат описан в `.claude/skills/fleet-step-report/SKILL.md`.
